# hill90-app — Product Requirements

**Status:** Living document — describes what is built and used today, not what is intended. Unproven and aspirational items are labelled as such in the text; do not read an unlabelled claim as more certain than its citation supports.
**Date:** 2026-08-07
**Companion:** [SPEC.md](SPEC.md) — service boundaries and contracts
**Why this exists:** app#503 (there was no PRD or SPEC for this repository) and Hill90#797 (Hill90's own PRD.md/SPEC.md are superseded and slated to move under `docs/`). This document is written as a description of what is true, dated, with every load-bearing claim tied to a test file, a commit, or a live check run against production or the local stack — not as a statement of intent. This repo, and the platform it runs on, has a documented, repeated failure where a written claim outlives the state it described and then gets reasoned over as if still true (see [SPEC.md §4](SPEC.md#4-known-documentation-drift) for three concrete instances found in the same week this document was written). A PRD that describes the desired end state, written in the present tense, becomes the next one. This one doesn't.

## What hill90-app is

An AI agent platform: agents run in sandboxed containers, reach language models through a policy-gated router, and share a persistent knowledge base with full-text search. A Next.js UI drives it, with SSE streaming for chat. It runs locally in Docker and, in production, as a **tenant** of the [Hill90](https://github.com/jonhill90/Hill90) platform — consuming Hill90's identity provider (Keycloak, realm `platform`), its PostgreSQL instance and its MinIO object storage, rather than running any of those itself. This is a governing architectural decision, not a detail: see [SPEC.md §0](SPEC.md#0-ground-truth).

The product is source code and infrastructure in this one repository. There is no separate packaged product, no external customers, and no billing.

## Who uses it

**Verified 2026-07-31 (CLAUDE.md), not independently re-verified for this document:** three real Keycloak identities exist in realm `platform` with `hill90-ui` client roles — `jon` (`admin, user`), `hill90admin` (`admin`), `testuser01` (`user`). The realm import ships zero users; all three were created by hand. There is no user self-registration path, and no evidence any identity beyond these three has ever authenticated against this app.

**The two people/roles this app actually has:**
- **Jon** — the operator and sole real end user. Signs in as `jon`, holds `admin`, uses the product directly and files issues against it in the same repository that implements it.
- **An agent developer/operator** — currently the same person, wearing a different hat: creates agent definitions (`SOUL.md`/`RULES.md`, tool grants, model policy), starts and stops them, reads their output.

**Not a real user population today:** `hill90admin` and `testuser01` exist for testing distinct role behavior (admin-vs-user gating) and for automated/manual verification work respectively — not as evidence of adoption beyond the operator.

## What is actually built and used (verified)

Ordered from most to least exercised, each claim cited.

1. **Agent creation via `POST /agents` is exercised end to end against a real Postgres.** `services/api/src/__tests__/integration/agents-create-matches-seed.test.ts` (added 2026-08-06, app#607) runs the real route against a throwaway Postgres and compares the resulting row to `platform-guide`, the one row this estate had long treated as a real example of what the route produces. **The comparison found a real mismatch**: the route's actual default `tools_config` does not match the seeded row's shape, and `container_profile_id` defaults to `null` where the seed carried an explicit reference. This is itself a corrected instance of the documentation-drift problem this document exists to avoid — see [SPEC.md §4](SPEC.md#4-known-documentation-drift).
2. **The chat callback boundary is proven, including all four token-rejection arms.** `services/api/src/__tests__/integration/chat-callback-contract.test.ts` (2026-08-06, app#608) exercises `/internal/chat/callback` against a real Postgres: a correctly-signed callback persists an assistant message and advances the SSE sequence cursor; a second callback for an already-terminal message is a no-op; and separately, each of (a) no `Authorization` header, (b) a wrong token of the same length (exercising the `crypto.timingSafeEqual` branch), (c) a wrong token of a different length (exercising the length short-circuit before that branch), and (d) a malformed header with no `Bearer ` prefix are rejected with `401` and leave the row untouched. A fifth, distinct case — no `CHAT_CALLBACK_TOKEN` configured at all — is rejected with `503`, deliberately not `401`, because "not configured" and "wrong credential" are different claims.
3. **`POST /chat/threads` (the first-message create path) is reachable end to end against a real Postgres.** `services/api/src/__tests__/integration/chat-first-message-reachable.test.ts` (2026-08-06) proves this, with one piece of stated test-only scaffolding: reaching a dispatchable agent state (`status='running'` with a `work_token`) normally requires starting a real container, which the test sets directly via SQL rather than driving the full orchestration path — that path is exercised separately (see agent lifecycle, below).
4. **Agentbox is the sole assembler of an agent's system prompt**, and as of `services/agentbox/app/runtime.py` (app#609, merged 2026-08-06 23:00 UTC), a missing or empty `SOUL.md`/`RULES.md` no longer fails silently. `RULES.md` carries the agent's operating constraints and fails **open** (the agent keeps answering, with no rules) — its loss now logs at `ERROR`. `SOUL.md` (identity/voice, not a safety boundary) logs at `WARNING`. Both emit a queryable `identity_load_degraded` event. **Neither condition stops the agent from starting** — a bad mount is treated as an operational fault to surface, not grounds for refusing to run. `services/api`'s `agent-files.ts` writes these two files to disk as part of provisioning; it does not itself assemble a prompt from them.
5. **No human conversation has ever completed end to end in production.** `chat_threads` holds **zero rows** — confirmed live against the production database (`hill90_api` on the platform Postgres) on 2026-08-07, the same day this document was written, and consistent with the read-only check the tests above cite from the day before. The `agents` table holds exactly two rows: `platform-guide` (the long-standing example agent) and `chat-path-proof-502` (created during a separate live investigation into the chat path, app#502) — both currently `stopped`. **A spec for a chat product whose chat has never been used by anyone says so, here, plainly: it has not.**

## What exists but is unverified, partial, or explicitly aspirational

- **Sign-in.** Per CLAUDE.md (2026-07-31), a real authorization-code login by `testuser01` against realm `platform` succeeded and is recorded in Keycloak's own login-event log. This document does not re-verify that claim independently; it is cited from CLAUDE.md's own dated record, which itself replaced an earlier, wrong claim in the same file that no human had signed in. Treat sign-in as **working, dated 2026-07-31**, not as continuously re-proven.
- **The full agent lifecycle beyond creation** — starting a container, dispatching real model inference through the router, an agent replying via the callback boundary above, in one unbroken chain, initiated by a real signed-in human through the UI — **has not been exercised end to end and is not claimed to be.** Each individual link has been proven separately (agent creation: above; the callback boundary: above; agentbox's own runtime behavior: above and in `services/agentbox`'s own test suite) but the full chain, human-initiated, has not.
- **Invitations and role assignment from an admin UI** (app#500) is under active, incremental construction. As of this document, only a read-only user list exists (app#611, not yet merged) — no write path, no invitation flow. The design note on app#500 additionally found that the realm's SMTP configuration, a prerequisite for any invitation email, has a blank password field in the checked-in realm export; whether Keycloak can actually send mail today is an **open, unverified question**, not assumed to work.
- **`services/cli` and `services/discord-bot`** exist in the repository with no deploy wiring (`README.md`, "What it is" table) — they are not part of the deployed product today, however complete their own code may be.
- **Consolidation of the app's remaining infrastructure onto the platform** — the Keycloak-realm and Postgres halves are done (2026-07-31, per CLAUDE.md); MinIO consolidation is, per the same source, an **open, undecided question**, not a completed step. `README.md`'s own "Consolidation" section describing this as partly-pending is itself dated 2026-07-29 and predates both completions — read CLAUDE.md, not that section, for the current state. This is itself an example of the drift this document is trying not to repeat; see [SPEC.md §4](SPEC.md#4-known-documentation-drift).

## Non-goals

Stated because they have been asked and settled, not because they are self-evident:

- **Not a multi-tenant SaaS product.** One operator, no external customer accounts, no billing surface.
- **Not its own identity provider, database, or object store in production.** These are deliberately consumed from the Hill90 platform; standing up a competing instance of any of them is a regression, not a feature (see the retired `app-postgres`, `app-auth.hill90.com` Keycloak, and the open MinIO question in SPEC.md §0).
- **Not proven reliable at scale or under real conversational load.** With `chat_threads` at zero, there is no load to have survived, and no claim of reliability under load is made here.

## Success measure, stated honestly

There is no adoption metric today because there is, verifiably, no adoption yet beyond the operator (§ "Who uses it"). The nearest honest measure of progress is **falsifiable claims proven against real infrastructure rather than assumed** — the pattern set by app#607/#608's real-Postgres tests and this session's live production checks. The next milestone this document can point to concretely is: **one human-initiated chat conversation completes end to end in production**, at which point `chat_threads` stops being zero and claim 5 above becomes the first thing in this document that needs updating.
