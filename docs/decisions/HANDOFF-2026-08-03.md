## The seam, and why it keeps producing

**Silent success: an operation that did not return everything and reported success.** It is
worse than an error because the user acts on it.

The generalisation that did the work: **a number that agrees with itself.** A total computed
from the page it describes cannot disagree with the page, so it reports truncation as
completeness and no test written against it ever fails. Every finding this session was an
instance — `len(rows)` in the knowledge service, `data.length` one layer up in the api,
`entries.length` one layer up again in the UI, `len(page.Entries)` in the Go CLI. Same
defect, four languages, four hops.

**Two questions produced everything.** They are the transferable part.

1. **Who reads this value?** Not "is it set" — *is anything consuming it.*
   `grep -rni "total-count" services/` returned four hits: two writes and two docstrings.
   **Zero readers.** The mechanism was in place and doing nothing, and walking the consumer
   list to answer that question is what surfaced the api regression (#188).
2. **What does the *other* consumer do?** Every endpoint had two. The UI would have rendered
   an empty page from a body object; the Go CLI would have hard-failed decoding it. Two
   consumers, two different failure modes, one cause — and the second one is what made the
   `X-Total-Count` design obviously right rather than merely defensible.

**A confident "dry" from a lane that has just stopped finding things is a hypothesis, not a
result.** CLAUDE.md already says this; it held again.

## The twin rule

**A fix applied to one route and not its sibling is how one of them stays broken for a
year.** It predates this session — CLAUDE.md records #141 (clamp on the export endpoint,
not its twin) and #153 (the fix went to one route, not the other).

It was re-proved twice today, both times by us:

- #182 bounded `/internal/admin/entries` and deliberately left the agent-facing twin
  unbounded. Filing it as an issue and fixing it in the same PR (#183/#186) is the only
  reason it did not sit.
- #188 is sharper: **bounding the endpoint broke a count that was previously correct.** The
  api derived `knowledge_entries` from `data.length`, which was the true total until the
  page was capped at 500. A regression introduced by the fix for the very family it belongs
  to. It is recorded as ours, not as a limitation, because that is the only version worth
  reading.

The operational form: **when you bound something, go find who was counting on it being
unbounded.**

## The positive-control rule

**The fixture must make the two numbers DISAGREE, and you must watch it fail first.**

3 rows, `limit=2`, assert the total is 3 *while the array length is 2*. A fixture with fewer
rows than the limit makes them equal, and a `len(rows)` implementation passes it — so a test
written only against the correct implementation cannot tell the two apart and would ship the
defect it was written to prevent.

The Go test asserts the fixture's own numbers differ, so the control cannot rot into one that
proves nothing. Do that again elsewhere.

**Corollary, learned twice today:** a check that inspects nothing passes for the wrong reason
and looks exactly like health. The bats guard reported `OK` having parsed zero stacks (a
BSD/GNU `sed` difference), and only its own vacuous-inspection assertion caught it.

## Two calls that look inconsistent and are not

An absent `X-Total-Count` is handled **opposite ways** in two places, on purpose:

- **api (#190):** fall back to `data.length`. An upstream with no header is an upstream with
  no `LIMIT`, so the array genuinely *is* every row.
- **ui (#191):** never fall back — render "2 shown", not "2 entries". A stale hop *in front
  of* a bounded knowledge sends no header either, so the length proves nothing.

**Same signal, different inference, because the position in the chain differs.** If someone
"harmonises" these, they will reintroduce the defect on one side.

## Numbers worth keeping

Host-verified 2026-08-04, after the deploy — `app-api` **53.13 MiB**, `app-ui` **37.9 MiB**,
`app-mcp` **52.98 MiB**, each now against **512 MiB** rather than the full 15.61 GiB.
Platform baseline **16 by name, 0 unhealthy**. Nothing was OOM-killed on the way in, which
was the live risk of a ceiling derived from an idle sample.

**The limits are still derived from ONE instantaneous sample, not a peak**, and no peak
exists to check against: **cAdvisor on that VPS emits no container identity at all**
(`{__name__=~"container_.*", name!=""}` → 0 series; Hill90 `alert-series-verification.md`,
verified 2026-07-31). So per-container memory has never been in Prometheus, nothing can alert
on these ceilings, and **a 137 exit is evidence the number is wrong, not the approach.**

One number kept but not acted on: `app-mcp` peaked at **297.5 MiB** locally over two days,
against 52.98 MiB on the host. It is the only evidence either way that mcp spikes well above
rest. **If mcp is ever OOM-killed, that is the first thing to question.**

## Two limits on today's evidence, so it is not read wider than it is

1. **The `services/api` findings in [#183](https://github.com/jonhill90/hill90-app/issues/183)
   are a reachability judgement made by READING. None were exercised** — no request sent, no
   row count taken.
2. **"Unbounded" means grows without a ceiling, not is already large.** No production row
   counts were measured.

An unmeasured judgement labelled as one is useful; labelled as a measurement it is a trap.

## What I would ask first with no memory of today

1. **Has anything been OOM-killed?** `docker ps -a --filter name=app-` and read the exit
   code — **137** is the answer. It is the one live risk this session created, it cannot be
   alerted on, and nothing will tell you unless you look.
2. **Who reads the value?** Before adding a mechanism, and before believing an existing one
   works. It is the question that found the regression, and the one nearly skipped once both
   endpoints were bounded and the header was in place — *and unread*.

A third, if the session is picking up #184 or #185 rather than something new: **run the
control against the broken implementation before writing the fix.** Watching it fail is the
step that cannot be recovered afterwards.
