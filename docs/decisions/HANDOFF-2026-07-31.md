# Handoff — the tenant, 2026-07-31

**Written 2026-07-31.** Covers **hill90-app**. The estate-level view — the platform's
retirements, credential rotations, baselines and the reboot question — is the platform
repo's
[2026-07-31 handoff](https://github.com/jonhill90/Hill90/blob/main/docs/decisions/2026-07-31-handoff.md).
This one deliberately does not repeat it; where they touch, this points there.

Perishable claims carry a date. Where something was measured, the number is here; where

## The one-sentence version

**The app is now a tenant in fact, not just in design: it consumes the platform's
identity, data and object storage, and its own copies of all three are gone or stopped.**
Local development still runs the app's own services, deliberately, and that gap is an
open decision rather than an oversight.

## What the app consumes now

| Concern | Was | Is, as of 2026-07-31 |
|---|---|---|
| Identity | `app-keycloak`, realm `hill90` | platform Keycloak, realm `platform`, **client** roles on `hill90-ui` |
| Data | `app-postgres` | platform Postgres — `hill90_api`, `hill90_akm`, `hill90_litellm`, owned by `hill90_app` (`superuser=false`) |
| Object storage | `app-minio` | platform `minio`, via the scoped `tenant-hill90-app` credential |

**Authorization is by client role, not realm role.** Realm `platform` also has a realm
role named `admin`, and holding it grants no application access. Anything reading
`realm_access.roles` for authorization is wrong.

### Proven by traffic, not by configuration

Configuration naming a database or a bucket is not evidence that anything reaches it.
Each was proven by a real object or a real row, through the app's own client code:

- **Object storage**, `Verified 2026-07-31 02:15 UTC` — a script run *inside* `app-api`,
  importing app-api's own compiled S3 client and its deployed environment: PUT, GET,
  byte-for-byte round trip, and `CreateBucket` correctly refused with `AccessDenied`,
  which is what proves the credential is the scoped one and not root. Counts on both
  sides: platform `user-avatars` went 0 → 2, `app-minio` stayed 0 across all buckets.
- **Database**, same method — a query through app-api's own pool module returned
  `hill90_api` as `hill90`, 32 public tables, PostgreSQL 16.14.
- **Identity** — `testuser01` completed a **real authorization-code login** against realm
  `platform`, and a `LOGIN` row is now readable from the platform Postgres. The estate can
  finally answer "did this user log in, and when"; see the platform's
  [keycloak-login-events runbook](https://github.com/jonhill90/Hill90/blob/main/docs/runbooks/keycloak-login-events.md).

## What remains of the app's own three

Full detail and exact backup paths are in the platform handoff's *Retired* table. What a
tenant reader needs:

- **`app-keycloak` — gone.** `app-auth.hill90.com` returns 404. Realm `hill90` is gone
  from the live directory; it survives in a realm export **with users** held on the VPS,
  and inside the retained tenant database volume.
- **`app-postgres` — gone; its volume `prod_app-postgres-data` deliberately kept**,
  alongside dumps of all five databases, restore-proven per table before removal.
- **`app-minio` — stopped 2026-07-31 01:40:43 UTC, not removed.** Container `Exited (0)`,
  volume `prod_app-minio-data` retained.
  **Retention expires 2026-08-01 01:41 UTC** — one full day unused.

> **The stopped `app-minio` still carries its Traefik labels.** Traefik only builds routers
> for running containers, so today exactly one router claims `storage.hill90.com`. But
> `docker start app-minio` would recreate the collision, and because *both* backends are
> MinIO the host would answer **200 either way** — it would look fine. If anyone starts it
> to inspect the old data, stop it again before walking away. Removing the container is
> what finally removes the labels.

The compose files for all three are **kept on purpose**, with retirement banners, because
local development layers on them. `scripts/deploy.sh db` and `deploy.sh auth` refuse.

## Local development — the real state

Local runs the app's **own** Keycloak, Postgres and MinIO. That is a restoration of how
local worked before the cutover, **not** parity, and it means a local test proves the
realm design but not the tenancy. Whether to change that is
[an open decision](local-parity-with-platform-services.md).

Three things were fixed today, each found only by starting from nothing:

1. **The platform keys were missing and nothing caught it.** The retirements made the
   production compose files read `PLATFORM_DB_*` and `MINIO_TENANT_*`; the local overrides
   layer on those files, and `.env.local.example` never gained the keys. Compose does not
   fail on an unset variable — it substitutes an empty string — so `api`, `ai` and
   `knowledge` were handed `postgresql://:@:5432/hill90_api`. Since #61 `ai` fails closed,
   so a clean start failed outright. The running stack hid it because nobody had restarted.
   Fixed in **#71**, for fresh clones *and* existing files, and `local.sh up` now runs the
   same interpolation gate `deploy.sh` has always had — which is why production would have
   refused this and local did not.
2. **litellm's healthcheck could not survive a first run** (**#77**, **#79**). On an empty
   database it applies its whole prisma migration set before binding the port: **measured
   172s**, against a `start_period` of **15s**. It was marked unhealthy, and `app-ai`'s
   `condition: service_healthy` aborted the entire `up`. Fixed in **both** declarations —
   the production/tenant file and the standalone fork, which had the same defect at 30s.
3. **Local was creating production-named volumes.** `VOLUME_PREFIX` was set nowhere
   locally, so `${VOLUME_PREFIX:-prod}` produced `prod_app-postgres-data` on a laptop —
   invariant 3 broken in exactly the way invariant 4 warns about. Now `hill90dev`.

Measured cold-start budgets for every service are in
[cold-start-budgets.md](../runbooks/cold-start-budgets.md). They are laptop numbers
against the tenant path; nothing has been measured on the VPS.

**Why litellm survived so long is the lesson worth keeping:** 172s on a true first run,
**96s** once the prisma engine layer is cached. Against the old 105s budget the fast run
passes and the slow one fails — a defect that appears and disappears with a layer cache,
and heals itself a minute later, so no subsequent run ever showed it.

## The api test suite — a green run is not evidence

`Re-measured 2026-07-31: 7 of 20 runs of current main fail.`

This is the honest item, and it should not be softened. Read
[api-suite-flakiness.md](api-suite-flakiness.md) before citing a CI result.

**Killed by measurement, not by argument:**

| Hypothesis | How it died |
|---|---|
| `--runInBand` fixes it | **Refuted twice** — it makes it *worse*. Do not propose again |
| One culprit test file | Excluding the streaming-connection file gives 6/10 — no better |
| Positional mock queues as the *necessary* cause | A file with zero `Once(` reproduces it |
| Stale sweeper / workflow scheduler firing during tests | Both start only in `index.ts`; tests build from `app.ts` and never call them |
| Late fire-and-forget audit **database** writes | `helpers/audit.ts` is a synchronous `console.log` with no pool access |
| Leaked timers crossing the test boundary | Clearing them at the boundary still failed 6/20 |
| A router-mounting race producing framework 404s | **470 404s captured**; 455 were handler-generated JSON. Explanation dead |

**And the part that matters most:** the SSE timer leak was **real**, the fix in **#76** was
**right** — registered before the awaits rather than in a `finally`, with a test that fails
when it is removed — and it **did not move the rate**: 7/20 after. A correct fix that
changes nothing is still a correct fix, and it is also still not the cause.

**There is currently no outstanding hypothesis.** If someone forms one, write it into that
record *before* working on it, so the next dead end costs one session rather than two.

**Operational consequence:** a green run of the api suite is not evidence that a change is
safe, and should not be cited as one until this is fixed. The other six suites are
unaffected.

## Terminal WebSocket hardening — proven in production

`Verified 2026-07-31.` Two defects fixed: the upgrade handler never read
`req.headers.origin`, and the token was read from the **query string** before the
`Authorization` header — and URLs reach access logs, proxy logs and browser history.

The token now travels as a WebSocket subprotocol, and **Origin is checked before the
credential is examined**, so a refused origin cannot learn whether the token it captured
is valid.

One genuinely valid `testuser01` token, used three times, varying only where it is carried
and which Origin declares it:

| Request | Observed |
|---|---|
| valid token in subprotocol, Origin `https://hill90.com` | **`101 Switching Protocols`** |
| **same** token in subprotocol, Origin `https://evil.example` | **`403 Forbidden`** |
| **same** token in the **query string**, Origin `https://hill90.com` | **`401 Unauthorized`** |

Three different codes from one token is what makes this a proof rather than an assertion.
**A blanket 401 means you are measuring nothing** — that happened twice, once before the
fix and once through an HTTP/2 probe that never reaches the upgrade middleware. Force
HTTP/1.1 and carry a real token.

## Open — Jon's, not a lane's

1. **The `api.hill90.com` rate-limit asymmetry.** The UI carries the shared rate-limit
   middleware; the API carries no middleware at all. **Not an exposure** — the API is meant
   to be public and authenticates its callers — but the asymmetry looks unintended rather
   than decided, and the API is the more attackable of the two. The proposal is to attach
   the *same* middleware, on the grounds that the identical limit is already proven in
   production on the UI, so it is the lowest-risk value available. **The platform owns the
   middleware definition; the tenant owns the reference — so the change belongs in this
   repo's compose file.** Not implemented. Awaiting a decision.
2. **Repository visibility, and the history rewrite.** Costs are measured, not estimated:
   **59** commits contain the tailnet address, **380** contain the SSH alias, and the author
   email is metadata on essentially every commit — so removing it rewrites all **619** SHAs.
   All three tags point inside the range and 74 squash-merged PRs record SHAs that would
   cease to exist. By what an attacker gains the order is **SSH alias > email > tailnet
   address**, the reverse of the removal cost. The current tree contains none of it — the
   exposure is history-only — and the repo is still private, so **a rewrite before first
   publication is effective and one after is not.** Full costing in
   [publishing-and-history-rewrite-cost.md](publishing-and-history-rewrite-cost.md).
   **No recommendation: risk tolerance is the input, and that is Jon's.**
3. **Whether local moves onto the platform services** — see the parity record above.
4. **`app-minio`'s removal** after 2026-08-01 01:41 UTC. Removing the container is
   reversible while the volume exists; deleting `prod_app-minio-data` is the irreversible
   step and deserves to be a separate decision.

## The habit worth keeping

Nearly every defect this cycle was found the same way: **by starting from nothing, and by
distrusting a check that returned nothing.**

`ls -l` hiding a dotfile read as "the file is absent". `grep` for a compose warning whose
quotes are backslash-escaped read as "compose is silent". A `wc -l` on a bad `mc` alias read
as "zero objects". Each looked like a clean result. The rule that survives all of them:
**make a check produce a positive result on a known input before believing a negative one on
an unknown.**
