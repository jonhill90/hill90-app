**The SQL gate proves parsing, not correctness.** `scripts/checks/check_sql_identifiers.sh`

a statement that parses returns the right rows. A wrong `JOIN` passes it.

**56 statements are not checkable at all, and the number is printed on every run.**
Today: `files scanned: 76   checkable: 287   NOT CHECKABLE (interpolated): 56`. Those 56
are built by string interpolation, so no parser sees them, and the gate counts them
rather than folding them into the pass — an unchecked statement is not a passing one.
If that number climbs, coverage is falling while the check stays green.

## 0B. `process.exit()` does not wait for a pending write — three times today

A fix that logs and then exits **loses the log**. This is not a subtlety about stderr;
it is a property of `process.exit()` and it applies to any pending write, including a
socket.

It decided three separate designs today, which is why it belongs here rather than in one
file's comments:

1. `services/api/src/boot/fatal.ts` — `console.error(...)` then `process.exit()` lost the
   message when stderr is a pipe, which in a container it always is. The fix that made a
   failed startup fatal would have produced *a process that dies without saying why* —
   the exact failure it exists to prevent. Caught by reading a real child process's
   stderr and finding it empty.
2. `services/discord-bot/src/index.ts` — the same flush before exit on a failed login.
3. `services/api/src/services/terminal-proxy.ts` — the shutdown drain exists because a
   close frame is a write, and the exit will not wait for it.

**Anything that logs a cause and then exits must let the write happen first** — one
`setImmediate` is enough, and all three do exactly that.

## 0C. The realm hazard runs BACKWARDS, and a rebuild is how it fires

**Doing the obvious thing breaks production.** This is the one place in the estate where
that is true today, so it must not be discovered by someone rebuilding the VPS.

```
LIVE production hill90-ui:      web-origins, acr, profile, roles, basic, email   <- basic PRESENT
committed platform-realm.json:  web-origins, acr, roles, profile, email          <- basic ABSENT
```

Keycloak 26.4 emits the **`sub`** claim from the `basic` scope. The live client has it;
the file it is supposedly built from does not. **The live realm is correct and the
committed file is the broken one.**

So *importing the committed realm* — a rebuild, a disaster recovery, a fresh
environment, or a well-meant "make live match the file" — strips `sub` from every token.
`services/api` reads `user.sub` at 158 sites, and since #306 `requireAuth` **refuses** a
token without one. The result is not a subtle drift: **the API answers 401 to every user**.
Disaster recovery is exactly when nobody is placed to work out why sign-in stopped.

Two more things that make it easy to get wrong: `scripts/checks/upstream-realm-expected.json`
pins the scope list *without* `basic` and passes today, so the guard would certify the
regression. And the divergence exists because a client created through `kcadm`
(`keycloak.sh tenant-clients`) inherits the realm's default scopes while an *import*
applies exactly the list in the file — **the same repository produces two different
clients depending on which path made them, and nothing compares them.**

Fix order, and it matters: add `basic` to `platform-realm.json` (Hill90#704) FIRST, then
refresh this repo's guard. The reverse makes the guard fight the fix. **Do not touch the
live client; it is already right.**

## 1. The seam: a green that is compatible with total failure

`HANDOFF-2026-08-03.md` named silent success — a thing that fails and says nothing.
This session's seam is its instrument-side twin: **a check that passes, on a system
where the thing it certifies is completely broken.** Not a flaky check, not a wrong
assertion. A check structurally incapable of going red.

The worked example, in full, because the shape is the transferable part.
`scripts/checks/tenant-login-platform-test.sh` completed a real authorization-code
login and asserted four token claims. It printed four PASS lines on a morning when no
human could sign in locally at all — HTTP 400, `Invalid parameter: redirect_uri`. Line
32 hardcoded the redirect the UI was *supposed* to send, so the one parameter that was
wrong was the one parameter the check supplied itself. The client secret had drifted
the same way: grepped from `.env.local`, which is not the value the UI holds.

**Two questions found everything this session.** Both are cheap, both are askable of
any check, and neither requires understanding the code under test.

**Q1. Does this check get its inputs from the thing under test, or from its own copy?**

A copy is a hardcode with a nicer name, and it can be right on the day it is written
and wrong forever after. This found the redirect URI, then the client secret in the
same file, and the fix is now structural: every request parameter is read from the
running UI container, and a missing value FAILS rather than falling back — a fallback
is how the hardcode comes back. `tests/scripts/login-check-sees-redirect.bats` holds
that shape; 8 of its 9 tests fail against the pre-fix files.

**Q2. If the thing I am checking were entirely broken, would this result look
different?**

If the answer is no, the result is *cannot tell* — a third state, and a real answer.
Not clean. This question is what makes the rest of this document honest:

- `GET /usage` returning `total_requests: "0"` looked like a quiet period. It was a
  per-user filter matching nothing, because `user.sub` was `undefined` (see §3).
- Production's owner-bearing tables are empty, so the row count that was supposed to
  confirm or refute §3 confirms nothing (see §3).
- The 9 `skills` rows in production carry `created_by IS NULL` — and so do the same 9
  locally, on a stack where nobody created them. Seeded. They cannot discriminate
  either.

Q1 is about how a check is built. Q2 is about how its result is read. The defects
this session were found by the first; the *limits of what was established* come
entirely from the second.

## 3. The unknown that was settled later the same day — read §0C, not this

**This section described `hill90-ui` tokens as carrying no `sub` claim, in production
as well as locally, and called it the largest open unknown. The production half is
false and was disproved hours later**, by the cheap check this section listed as
"still unrun". It is rewritten rather than deleted, because how it was wrong is the
useful part.

What was true: `sub` comes from Keycloak's `basic` client scope; `hill90-ui` lacks it
**locally** and in the **committed** `platform-realm.json`; `services/api` reads
`user.sub` at 158 sites; and locally a non-admin created a platform-scoped resource
because the check compared against `undefined`.

What was assumed and should not have been: that production matched the committed file.
**It does not.** The live client carries `basic`, measured twice read-only, so
production tokens carry `sub` and those 158 sites receive a real subject today.

So the defect was **local-only in effect**, and the real finding is the inversion now
recorded in **§0C**: the live realm is correct, the committed file is broken, and
*importing* it is what would break production. `auth.ts` refusing a token with no `sub`
landed in [#306](https://github.com/jonhill90/hill90-app/pull/306), which is why that
import is now an outage rather than a silent drift.

The method note worth keeping: a row count could not settle it — every owner-bearing
table in production is empty, which looks identical whether the defect is absent or
total. **A configuration read settled in one command what a data read could not settle
at all.**

### Standing bounds, restated rather than cited by number

**The SQL gate proves parsing, not correctness — unchanged, worth repeating.**
`scripts/checks/check_sql_identifiers.sh` catches a statement that cannot parse (a
column that does not exist); it says nothing about whether a statement that does
parse returns the right rows. A wrong `JOIN` still passes. This was true before
tonight and nothing tonight touched it — it is repeated here because a cold reader
should not have to find it buried in §0A of an unrelated lane's section to know it
applies to every SQL-touching change either lane makes.

**The identity-guard control now exists, and it proves less than "the guard is
tested" would suggest.** `jest.identityguard.js` — the response-stamping instrument
that has run on every api suite since round fifteen — had zero committed,
automated verification for any of its three detection arms before tonight; the two
that were supposedly "controlled" had only ever been forced by hand, once, during
last night's investigation, with the result written into prose rather than kept as
a test. Tonight added `src/__tests__/identity-guard-control.test.ts`, and it proves
exactly two things, cleanly, across two full 117-suite parallel runs: the guard
stays quiet on a response this worker legitimately stamped (arm A), and it fires on
a response that arrives unstamped from something outside `ourPorts` (arm C, via an
in-process Unix domain socket — see below). **It does not prove the guard catches a
sibling jest worker's differently-stamped response** — arm B, FOREIGN STAMP — which
was built, found unreliable under real conditions, and deliberately removed rather
than shipped skipped (see #339 below). And even arms A and C together prove the
detection *logic*, not a faithful reproduction of the one real intruder ever
observed on this host (`LogiPluginService`/websocket-sharp, a TCP responder) —
arm C's UDS-based stranger exercises the same code branch that responder would trip
without being that responder. "The identity guard has a committed control" is true
and worth less than it sounds; know which third it doesn't cover.

**#179's third approach was confirmed by measurement, not by reading the source
convincingly.** The reasoning — that a Unix domain socket listener would be
in-process yet invisible to the guard's `ourPorts` exemption, because
`srv.address()` for a UDS server returns a path string rather than `{port}` — was
correct, but it was reasoning until a five-line throwaway script actually printed
`(srv.address()||{}).port` and a connected client's `remotePort` and both came back
`undefined`. That step happened before a line of the real control was written. Say
this plainly because it would have been easy to skip: a chain of correct-sounding
inferences about Node internals is not the same claim as a value observed on this
machine, and only one of those is safe to build on.

### #339 — genuinely unsolved, not parked

Arm B (FOREIGN STAMP) is not in the suite and not `test.skip`'d — it is out
entirely, with its full reproduction filed as
[#339](https://github.com/jonhill90/hill90-app/issues/339) so it is searchable
rather than sitting as a skipped block nobody revisits. State plainly what "not
parked" means here: this is not a known-cause fix deferred for time. It is a real
mechanism failure with the cause still unknown.

What is established: the control (using `__setStampForControl`, a hook that has
existed in the guard since it was written and had never once been exercised before
tonight) is 100% reliable alone — eleven consecutive isolated runs — and 100%
reliable under heavy artificial CPU load — six runs with the machine's cores pinned
by spin loops. It failed 2 out of 2 real full-117-suite parallel runs, both times
the same way: the response came back stamped with this worker's own correct,
un-overridden ID, as if `__setStampForControl` had never been called. Patch-stacking
across test files sharing one worker process — monkeypatched Node core modules are
not sandboxed per test file — was the obvious suspect and was ruled out directly,
not inferred: an instrumented run confirmed the guard's setup file executes exactly
once per worker process, not once per test file. Small hand-built reproductions (up
to ten sibling files, run before this one, both in-band and with two workers) never
reproduced it. Whatever triggers this needs either the real file count, the real
worker-to-file distribution, or some other suite-wide condition not yet isolated.

### Other standing facts from tonight, stated as bounds rather than a changelog

- **A live-shell exposure is closed.** A terminal WebSocket upgrade with a token
  carrying no `sub` used to fall through to `sub || ''`; it is now refused at verify
  time, before the upgrade completes, the same way `requireAuth` refuses an HTTP
  request with no `sub` since #306. Proven with a real HTTP status arriving on the
  wire for the refusal, not a promise rejection nobody would see.
- **CI's install step can no longer silently lose a native binary.** `npm ci`'s
  `optionalDependencies` can drop a platform-specific binary on a registry hiccup
  and still exit 0 — this is what turned #329 red for a reason that had nothing to
  do with the change under review. Both the `api` job (`sharp`/libvips) and the `ui`
  job (esbuild/rollup family) now verify the binary actually loads immediately
  after install, and fail there with a named cause, rather than downstream in a
  jest run that looks like an unrelated test failure.
- **An endpoint that works, was just repaired, and has no caller is Jon's decision,
  not a cleanup.** `GET /agents/:id/artifacts` was fixed hours before #8 removed its
  only UI consumer. It still exists server-side, still works, and nobody calls it.
  Confirmed, not assumed, in #334: the API does not compute or store level/XP
  anywhere else either — removing the UI did not leave dead machinery running
  behind it.
- **CPU throttling cannot currently be observed on this host.** `nr_periods` reads
  `0` on api, mcp and ui, meaning no cgroup CPU quota is installed at all — a zero
  throttle count is a tautology, not evidence of headroom. A CPU limit added today
  would fail silently (slow requests, not a dead container) with no instrument
  currently capable of showing it. No number was proposed for #200 on that basis.
- **A flake that never failed got fixed anyway, and the reason is now in the test
  file itself, not just the issue.** The "Recent Chats" widget's immunity to the
  ARRIVED-LATE race that hit "Active Agents" seventeen times was exposure, not
  structure — a shorter async chain, not a widget that cannot race. #117's test
  file now says so where the next person meets it.

### What I would do next, and why

Not blind bisection on #339 tonight — this was tried in small form already (ten
files, two orderings, no reproduction) and the next step that would actually move
it is capturing the *real* full-suite worker-to-file assignment from an actual
failing run (log `JEST_WORKER_ID` and file order via a minimal reporter) and
replaying that exact assignment in isolation, rather than another hand-picked
subset — the fact that arbitrary subsets haven't reproduced it is itself evidence
that scale or the real mix matters, not just "more files nearby." That is real work
with a real chance of landing on the cause, which is exactly why it is not
something to start at the end of a long session: a confident wrong answer here
would be worse than the honest "unsolved" #339 already states.

The second thing worth flagging, not doing: whether `__setStampForControl`'s
unreliability under real load is a control-authoring artifact or a hint about
`stampValue` itself being less safe to read-and-reset under real timing than its
synchronous-looking code suggests. If it is the latter, that is not scoped to arm
B or to this control — it would say something about the guard's own reliability
guarantees, which the rest of tonight's work (and #313, and everything upstream of
it) has been leaning on without question. Worth deciding early in whoever's next
session, before assuming it is purely a test-file problem.
