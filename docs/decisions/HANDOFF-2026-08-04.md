## 0A. Bounds that are still true — read before trusting any green

Three claims that a green run does NOT make, all of them measured today.

**Nothing is tested past the WebSocket handshake against a real agentbox.** #314 and
#317 built the first end-to-end terminal coverage this repository has ever had — the
refusal path, the 4002 credential deadline, the 4004 revocation close, the 1001
shutdown. **All of it runs against a stand-in upstream** injected through
`resolveUpstream`. No test has ever driven the relay against a real agent container, so
the pumps, the backpressure path under a real producer, and anything agentbox does with
the socket are exercised by nothing. Note the corollary that makes this worse than it
sounds: **no agentbox container has ever run in production either** (`docker ps -a` on
the host, `Verified 2026-08-04`), so neither the tests nor production have ever
exercised that path.

**The SQL gate proves parsing, not correctness.** `scripts/checks/check_sql_identifiers.sh`
asks Postgres to `PREPARE` every static statement, which catches the class that made
`/agents/:id/metrics` and `/agents/:id/artifacts` answer 500 on every call since they
were written — a column that does not exist cannot parse. It says nothing about whether
a statement that parses returns the right rows. A wrong `JOIN` passes it.

**56 statements are not checkable at all, and the number is printed on every run.**
Today: `files scanned: 76   checkable: 287   NOT CHECKABLE (interpolated): 56`. Those 56
are built by string interpolation, so no parser sees them, and the gate counts them
rather than folding them into the pass — an unchecked statement is not a passing one.
If that number climbs, coverage is falling while the check stays green.

## 0B. `process.exit()` does not wait for a pending write — three times today

A fix that logs and then exits **loses the log**. This is not a subtlety about stderr;
it is a property of `process.exit()` and it applies to any pending write, including a
socket.

It decided three separate designs today, which is why it belongs here rather than in one
file's comments:

1. `services/api/src/boot/fatal.ts` — `console.error(...)` then `process.exit()` lost the
   message when stderr is a pipe, which in a container it always is. The fix that made a
   failed startup fatal would have produced *a process that dies without saying why* —
   the exact failure it exists to prevent. Caught by reading a real child process's
   stderr and finding it empty.
2. `services/discord-bot/src/index.ts` — the same flush before exit on a failed login.
3. `services/api/src/services/terminal-proxy.ts` — the shutdown drain exists because a
   close frame is a write, and the exit will not wait for it.

**Anything that logs a cause and then exits must let the write happen first** — one
`setImmediate` is enough, and all three do exactly that.

## 0C. The realm hazard runs BACKWARDS, and a rebuild is how it fires

**Doing the obvious thing breaks production.** This is the one place in the estate where
that is true today, so it must not be discovered by someone rebuilding the VPS.

```
LIVE production hill90-ui:      web-origins, acr, profile, roles, basic, email   <- basic PRESENT
committed platform-realm.json:  web-origins, acr, roles, profile, email          <- basic ABSENT
```

Keycloak 26.4 emits the **`sub`** claim from the `basic` scope. The live client has it;
the file it is supposedly built from does not. **The live realm is correct and the
committed file is the broken one.**

So *importing the committed realm* — a rebuild, a disaster recovery, a fresh
environment, or a well-meant "make live match the file" — strips `sub` from every token.
`services/api` reads `user.sub` at 158 sites, and since #306 `requireAuth` **refuses** a
token without one. The result is not a subtle drift: **the API answers 401 to every user**.
Disaster recovery is exactly when nobody is placed to work out why sign-in stopped.

Two more things that make it easy to get wrong: `scripts/checks/upstream-realm-expected.json`
pins the scope list *without* `basic` and passes today, so the guard would certify the
regression. And the divergence exists because a client created through `kcadm`
(`keycloak.sh tenant-clients`) inherits the realm's default scopes while an *import*
applies exactly the list in the file — **the same repository produces two different
clients depending on which path made them, and nothing compares them.**

Fix order, and it matters: add `basic` to `platform-realm.json` (Hill90#704) FIRST, then
refresh this repo's guard. The reverse makes the guard fight the fix. **Do not touch the
live client; it is already right.**

## 1. The seam: a green that is compatible with total failure

`HANDOFF-2026-08-03.md` named silent success — a thing that fails and says nothing.
This session's seam is its instrument-side twin: **a check that passes, on a system
where the thing it certifies is completely broken.** Not a flaky check, not a wrong
assertion. A check structurally incapable of going red.

The worked example, in full, because the shape is the transferable part.
`scripts/checks/tenant-login-platform-test.sh` completed a real authorization-code
login and asserted four token claims. It printed four PASS lines on a morning when no
human could sign in locally at all — HTTP 400, `Invalid parameter: redirect_uri`. Line
32 hardcoded the redirect the UI was *supposed* to send, so the one parameter that was
wrong was the one parameter the check supplied itself. The client secret had drifted
the same way: grepped from `.env.local`, which is not the value the UI holds.

**Two questions found everything this session.** Both are cheap, both are askable of
any check, and neither requires understanding the code under test.

**Q1. Does this check get its inputs from the thing under test, or from its own copy?**

A copy is a hardcode with a nicer name, and it can be right on the day it is written
and wrong forever after. This found the redirect URI, then the client secret in the
same file, and the fix is now structural: every request parameter is read from the
running UI container, and a missing value FAILS rather than falling back — a fallback
is how the hardcode comes back. `tests/scripts/login-check-sees-redirect.bats` holds
that shape; 8 of its 9 tests fail against the pre-fix files.

**Q2. If the thing I am checking were entirely broken, would this result look
different?**

If the answer is no, the result is *cannot tell* — a third state, and a real answer.
Not clean. This question is what makes the rest of this document honest:

- `GET /usage` returning `total_requests: "0"` looked like a quiet period. It was a
  per-user filter matching nothing, because `user.sub` was `undefined` (see §3).
- Production's owner-bearing tables are empty, so the row count that was supposed to
  confirm or refute §3 confirms nothing (see §3).
- The 9 `skills` rows in production carry `created_by IS NULL` — and so do the same 9
  locally, on a stack where nobody created them. Seeded. They cannot discriminate
  either.

Q1 is about how a check is built. Q2 is about how its result is read. The defects
this session were found by the first; the *limits of what was established* come
entirely from the second.

## 2. The exercise result: one of three observed, and why not three

Eleven fixes merged before this lane started. Three of them had never been observed
in a running system — the usage gap row, the truncated-completion marker, the stream
error event. Exercising them was the point. **One was observed. Two were not, and the
reason changed twice.**

**Observed — the usage completeness qualifier (#261).** `GET /usage` against the
running local stack, real token, all three documented states seen rather than
inferred: a clean window (`known_missing_rows: 0`, `usage_write_gaps` present); a
window with a gap (`known_missing_rows: 3` with its first/last timestamps, sitting
next to a total of `0` — exactly the understated total the fix exists to qualify); and
the table absent, which returns **HTTP 200 with `unavailable: true`** and the totals
intact rather than 500ing the endpoint. That last one is the deploy hazard the PR
described, and it holds in the running service.

*What that does not cover, stated so it is not read wider than it is:* only the
reporting half. `usage_gaps.py` recording and converging a real failed write was never
exercised — it needs `services/ai` to run a `log_usage`, which is behind the same wall
as the other two. The gap row that was reported was a labelled fixture, inserted and
deleted.

**Not observed — the stream error event (#259) and the truncated-completion marker
(#260).** The first wall was real and is now down: `ANTHROPIC_API_KEY` and
`OPENAI_API_KEY` were present-but-**empty** in `.env.local`, so LiteLLM answered 401
before any stream began and the mid-stream break those fixes mark could not occur.
Both were populated from SOPS, LiteLLM now serves 200+ models, and
`hill90/agentbox:latest` plus `hill90/agentbox-monitor:latest` were built, since both
fixes live inside a running agent.

**The second wall is identity, and it is why they are still unobserved.** Reaching
either fix needs an agent, which needs a user model, which needs a provider
connection. Both halves are blocked:

- as a non-admin, `POST /provider-connections` succeeded but wrote `created_by = NULL`
  — the marking reserved for platform resources an admin must create — because
  `user.sub` is `undefined` (§3);
- as the seeded admin, `POST /user-models` returns `403 Requires user role`, because
  `requireRole` is a flat membership test and `admin` does not imply `user` (#277).

Completing that chain requires granting a role to an account. **That is changing auth
configuration to make an observation possible, which is how a green result stops
meaning anything, so it was not done** — the same call the previous lane made in #271,
for the same reason. Whoever picks this up: the unblock is #277 and #278 being
decided, or a deliberate, recorded decision to grant local roles. Not a quiet one.

## 3. The largest open unknown: #278, and the test that would settle it

**Access tokens issued to `hill90-ui` carry no `sub` claim.** Keycloak emits `sub` via
the `basic` client scope; the realm has that scope (mappers: `auth_time`, `sub`) and
`hill90-ui` does not have it among its defaults — `web-origins, acr, roles, profile,
email` — identically in the live local realm **and in Hill90's committed
`platform-realm.json`, which is the file production imports.**
`services/api/src/middleware/auth.ts:39` assigns the verified payload straight
through, requiring `exp` and nothing else, so `user.sub` is `undefined` at **158**
call sites in routes alone.

Observed locally, `Verified 2026-08-04`: a non-admin creating a platform-scoped
resource without the admin check ever being reached, and a per-user filter returning a
clean empty window because it could not match.

**Production was measured, and the measurement cannot decide it.** Every owner-bearing
table is empty — `chat_threads`, `agents`, `chat_messages`, `notifications`,
`provider_connections`, `user_models`, `workflows` all at 0; only `skills` has rows, 9
of them, which are seeded and NULL locally too. A database with no user-created rows
looks *exactly the same* whether `sub` is present and this defect does not exist
there, or `sub` is absent and every write through that path would land NULL. The count
agrees with both, equally. Logged as *cannot tell* — Q2, on our own work.

**The discriminating test is a decoded production token, not a row count.** A person
signs in at `hill90.com`, then `GET /api/auth/session` on that origin; decode the
`accessToken` locally and print the claim **names** only, never the token and never a
value. `sub` in that list or not ends the question. **That is Jon's to run** — no
agent should be completing an interactive login against production identity, and
nothing in this lane has production access.

Cheaper and still unrun: read `hill90-ui`'s default client scopes off the production
Keycloak with `kcadm` — config only, no login, no human. It settles the mechanism
without a token. The exact commands, with the positive control that stops an empty
answer being misread as `basic` absent, are in #278.

**Independent of how the realm is settled: `auth.ts` should refuse a token with no
`sub`, the way it already refuses one with no `exp`.** That is this repo's to make, it
waits on nobody, and it converts every future occurrence from a silent NULL into a 401
that names itself.
