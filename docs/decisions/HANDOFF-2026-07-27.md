## Decisions I made without you — all reversible

1. **The app keeps its own Postgres, Keycloak and MinIO** rather than consuming
   Hill90's. Evidence: Hill90's Postgres has one role (`hill90`, different
   password) and a health check that *asserts* platform-only databases; Hill90's
   Keycloak serves realm `platform` only (`hill90` is a live 404) and its clients
   are `grafana`, `portainer`, `hill90-vault` — all infra SSO. **Caveat I want to
   flag: the Keycloak half of this is weaker than the Postgres half.** Adding an
   app realm to Hill90's Keycloak is one bind-mount line. If you want one
   Keycloak, that decision is cheap to reverse.

2. **Naming scheme: Hill90's convention plus an `app-` tenant component.**
   `container_name: ${CONTAINER_PREFIX:-}app-<name>`; service keys get `app-` only
   where they collide (`app-postgres`, `app-keycloak`, `app-minio`,
   `app-postgres-exporter`); Traefik router names all `app-*`; the app's Keycloak
   hostname is `${APP_AUTH_HOST:-app-auth}`. Verified zero overlap against the
   live VPS's 13 containers. Alternatives I rejected, and why, are in the decision
   record — the main one is uniform `app-` on every service key, which is more
   future-proof but rewrites ~20 internal URLs.

3. **`postgres-exporter` is kept, not deleted.** I had earlier concluded it should
   be deleted as an infra duplicate. That was wrong and I reversed it: Hill90's
   exporter monitors Hill90's database and cannot scrape the app's, so deleting it
   would have silently ended monitoring of the app's Postgres.

4. **Override layer targets the prod files, not a fork.** `deploy/compose/overrides/`
   mirrors Hill90's structure.

### Retractions — read these before trusting anything above

An adversarial subagent audit found both of these in my own work.

**1. The `postgres` collision is MASKED, not removed.** This is the one most
likely to bite someone. Only the Postgres *container* moved to `app_internal`; in
the `compose/local.yml` overlay its consumers stayed dual-homed on
`<prefix>_internal`, which still answers to `postgres` with Hill90's instance:

```
hill90-minio: postgres -> 172.21.0.9    (Hill90's)
hill90-api  : postgres -> 172.26.0.2    (the app's, 30/30 lookups)
REACHABLE: hill90-api -> 172.21.0.9:5432
```

Nothing fails today only because Docker's resolver consistently prefers one
network. **That is not a fix, and it will resurface the moment resolver ordering
changes.** The prod path does not have this problem — renaming the service keys to
`app-postgres`/`app-keycloak` removed the ambiguity properly there. The overlay on
the fork still does.

**2. `README.md` asserted a "Verified cold" 200 for
`auth.localtest.me/realms/hill90`.** That 200 was only ever obtainable *because the
app was hijacking Hill90's hostname* — the exact thing this branch stops. Against
the current tree it is a 404. The dated evidence block is annotated as superseded
rather than rewritten.

**3. The Keycloak half of the dedup decision rests on weaker evidence than the
Postgres half, and I presented them with equal force.** Postgres has an *enforced*
boundary: Hill90's health check asserts platform-only databases and really fires.
There is no realm equivalent anywhere in Hill90's checks, and adding an app realm
to Hill90's Keycloak is **one bind-mount line**. "Cannot serve this app as
provisioned" is true; "would break the same separation boundary" is an argument
about intent dressed as the same class of evidence. If you want one Keycloak, that
decision is cheap to reverse.

### The `api.localtest.me/` 404 is correct behaviour — settled with evidence

This was chased for hours as a bug. It is not one. `services/api/src` mounts 25
route prefixes and **none of them is bare `/`**:

```
app.get('/health'   app.get('/me'      app.use('/agents'   app.use('/chat'
app.use('/skills'   app.use('/storage' app.use('/docs'     app.use('/openapi.json'  ...
```

`services/api/src/openapi/openapi.yaml` declares 102 paths; `/` is not among
them. Live confirmation that the router works and only the path is absent:

```
api.localtest.me:8080/              404      <- no such route, by design
api.localtest.me:8080/health        200
api.localtest.me:8080/me            401      <- auth enforced
api.localtest.me:8080/agents        401
```

It is the same shape as `ai.localtest.me`, which correctly 404s at `/` because its
router matches only `PathPrefix(/mcp)`. **No fix was made, because nothing is
broken.**

**How to tell the two apart in future.** Traefik's own 404 — meaning not routed —
is `Content-Type: text/plain` with body `404 page not found`. An application's 404
— meaning routed, no such path — carries the app's headers, here
`X-Powered-By: Express`. I made this mistake twice myself before checking the
router rule: I probed `app.localtest.me` against a UI router whose rule is the
apex domain. Check the rule, then the emitter, before calling it a bug.
